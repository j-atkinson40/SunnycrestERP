## VERDICT — the thesis holds. Park is mostly assembly of proven parts.

The load-bearing claim ("every existing surface is park-able; park reuses the
re-host contract, WidgetChrome/@dnd-kit drag, the pointer-events tier contract,
the S-3a escalation crossing, and the §5.6 return-pill") **is confirmed against
code.** Park has **two genuinely-new builds** (a multi-act session store; an
act-type→Focus escalation-resolution layer the registry doesn't provide today)
and **one bounded external gap** (no free-form email compose/send endpoint). None
of the three STOP conditions fired.

## Deliverable 2 — The genuinely-NEW seams (what park BUILDS vs. assembles)

**Park builds three things. Everything else is assembly.**

1. **The multi-act session store (NEW — the core build).** No existing container
   holds N *independent live acts, each with its own draft/dirty state, each
   committing independently.* `CommandBarSurfaceHost` = read-only surfaces derived
   from one context (cap 3, no per-surface draft). The Focus canvas = geometry-only
   widgets around one core (one act + satellites). `AncillaryPoolPin` = one widget.
   Park needs a session store tracking **the set of open tablets** — each tablet's
   `{actType, draftState, position/geometry, commitStatus}`. It borrows the @dnd-kit
   geometry machinery (which moves geometry-only widgets) but layers per-act draft
   ownership on top. *Evidence: `CommandBarSurfaceHost.tsx:14-22,91,99-100`;
   `Canvas.tsx:274-301`; `focus-context.tsx:411-447`.*

2. **The act-type → Focus escalation-resolution layer (NEW — the boundary the
   spec assumes but the registry doesn't provide).** The spec's predicate is "does
   this act-type have a *registered Focus*? → escalate." **The Focus registry
   cannot answer that.** `FocusConfig` is keyed by opaque id (`id, mode, displayName,
   defaultLayout, coreComponent, compositionFocusType, queueId`) with **no
   act-type/intent field**; `getFocusConfig(id)` matches by exact Focus-id only.
   Today the escalation target is hardcoded at the trigger site (`CommandBar`
   imports the literal `QUOTE_FOCUS_ID`, gated on `entryIntent==="quote"`). Park
   needs a real mapping — act-type → Focus-id — so the predicate is data-driven as
   the spec intends. This is a small layer, but it is genuinely new (see Type B #1).
   *Evidence: `focus-registry.ts:180-235,255`; `CommandBar.tsx:975-978`.*

3. **The ephemeral session lifecycle (NEW wiring, proven pattern).** A park session
   lives in client memory (React context), dies on exit, and offers a grace-window
   relaunch pill. The *pattern* exists (`lastClosedFocus` + return-pill); park needs
   the **list-shaped** version: snapshot the working set on exit → hold it for the
   grace window → `relaunchParkSession()` re-materializes all tablets → reap after
   the window. No server persistence (the anti-pattern is S-3b's `focus_sessions`).
   *One boundary condition to rule on: pure React state dies on hard reload/tab
   close; if "relaunch after an accidental reload" is in scope, a thin `sessionStorage`
   timestamp breadcrumb — not a server row, not `localStorage` — is the minimum, still
   client-only and non-cross-session (Type B #2).*

**Assembled, not built:** the re-host contract, the drag/resize/8px substrate, the
pointer-events contract, the return-pill timer, the escalation crossing mechanism,
the client-memory store pattern, the tier-cascade shape.

**One bounded external gap (not park's to build — flag it):** there is **no
generic compose-and-send-arbitrary-email endpoint.** `email_inbox.py` is inbox
management only (read/archive/flag/snooze/labels; no `/send`, `/compose`, `/reply`,
`/draft`). All outbound email today is template-bound transactional send via
object-specific routes (`/sales/invoices/{id}/send`,
`/price-management/send-price-list`, etc.). So a park act "fire off a free-form
email to X" has no backend seam until the Email Primitive (§3.26.15, Phase W-4b)
ships compose→send. **Every other park act commits through an existing endpoint**
(notes: customer/vendor/FH-case; quote/order create; FH-portal message;
transactional email sends). This shapes the slice-1 act catalog (Type B #3).

## Deliverable 3 — Escalation predicate + escalate-vs-light enumeration

**Predicate (spec):** "does this act-type have a registered Focus?" → escalate;
else stay light. **Registry reality:** answerable only after park adds the
act-type→Focus-id mapping (Deliverable 2 #2). Once that mapping exists, the
predicate is deterministic and data-driven exactly as the spec wants.

**Registered Focuses today (real):** `quote-building` (editCanvas,
`QuoteFocusWithAccessories`) and `funeral-scheduling` (kanban,
`SchedulingFocusWithAccessories`). All else is dev-test stub or one queue-bound
`decision-triage`.

**Escalate-vs-light for the spec's six example acts** (strictly from actual
registry contents):

| Park example act | Registered Focus today? | Result |
|---|---|---|
| reply-to-DM | none | **LIGHT** (stays in park) |
| email a customer | none | **LIGHT** |
| add a note | none | **LIGHT** |
| price lookup | none (read-only reference surface) | **LIGHT** |
| open a record | only `test-single-record` stub (no core, no mapping) | **LIGHT** |
| **build a quote** | `quote-building` (real) | **ESCALATE** → S-3a crossing |

**This confirms the spec's DM-fan-out scenario precisely:** the three DM acts
(reply / email / note) are all light and coexist in park; only a quote escalates.
The registry keeps the large majority of acts light today, which is the correct
default — park stays light until an act-type earns a Focus.

**What the escalation carries:** the target core's exact params shape. For
`quote-building` that is an `ExtractionContext` seeding `seedFromExtraction`. A park
quote act must hold/produce that shape to hand off (the S-3a crossing, generalized
to fire from a park tablet instead of the overlay chip).

## Deliverable 4 — First-slice scope recommendation + LOC floor

**Recommended slice 1 — "the DM fan-out + one escalation," using only existing
commit endpoints:**

Prove BOTH the working-set AND the boundary in one slice:
- **Summon 2–3 tablets from the command bar into park** and arrange them (drag,
  8px grid, WidgetChrome chrome) — a fan-out of LIGHT acts:
  - a **reference tablet** (re-host `entity-card.portal` or `surface.price-list-reference` — read-only, no commit),
  - an **add-note act** (commits via existing `POST /customers/{id}/notes`),
  - a **message/send act** (existing FH-portal or case send endpoint).
- **One escalation case:** start a quote in park → "Build this out →" → escalate to
  the `quote-building` Focus, reusing the S-3a crossing verbatim (park tablet calls
  `focus.open(QUOTE_FOCUS_ID, {params:{extraction}})`; §5.15 gate closes bar+park;
  Quote core seeds). Proves the boundary (light acts stay; Focus-shaped work leaves).
- **Ephemeral lifecycle:** park session in client memory; exit → grace-window
  relaunch pill (return-pill variant) → relaunch restores the tablets → reap.

**This slice proves the primitive** (multi-act working set, arrange, per-act commit,
escalation boundary, ephemeral relaunch) **without building everything.**

**Explicit DEFERS (flag as slice-2+):**
- Free-form email compose act (blocked on the Email Primitive / Phase W-4b endpoint).
- Full mobile three-tier cascade (slice 1 = desktop free-form only; the tier policy
  variant point is identified but the stack/icon park renderers defer).
- Smart-positioning engine (§5.7 "places new widgets in open regions") — slice 1
  uses simple placement; the shared positioning engine is a later "solve once well."
- The full act-type catalog (slice 1 = ~3 act types + quote escalation; the rest
  register additively against the mapping layer).
- `sessionStorage` reload-survival breadcrumb (only if Type B #2 rules it in).

**LOC floor — slice 1 only (scope-bounded, not a ceiling; per CLAUDE.md "scope is
the STOP gate, not a line count"):** roughly **~1,200–1,600 LOC**, concentrated in:
`ParkProvider` + multi-act session store (~250), `ParkCanvas` variant + park tier
policy (~250, mostly reused), `ParkHost` mount + command-bar summon integration
(~150), light-act tablet shells (note/message/reference) + WidgetChrome reuse
(~200), act-type→Focus mapping + escalation affordance (~120), return-pill park
variant + session snapshot/relaunch (~150), tests (~250). The STOP signal is scope,
not the number: if slice 1 starts needing a new drag system, a server session
table, a `?focus=` route for park, or the email endpoint, STOP and surface.

## Deliverable 5 — Type B calls (decisions for the human before building)

1. **Escalation-predicate mapping shape.** The registry can't answer
   "act-type → Focus" today. How should park resolve it?
   (a) add an `escalatesFrom: string[]` / `actType` field to `FocusConfig`
   (registry-native, data-driven — closest to the spec's "keyed to the Focus-type
   registry"); (b) a separate act-type→Focus-id map owned at the park layer;
   (c) hardcode per act like the command bar does today.
   **Recommend (a) or (b)** so the predicate is data-driven as specified.
   *(a) is the cleaner long-term shape; (b) is lower-risk for slice 1.*

2. **Ephemeral store: reload-survival.** Does the grace-window relaunch need to
   survive an accidental **tab reload / hard refresh**, or only a deliberate
   in-app exit? Pure React state dies on reload (spec-consistent with "dies on
   exit"); surviving an accidental reload needs a thin `sessionStorage` timestamp
   breadcrumb (client-only, clears with the tab — still non-cross-session).
   **Recommend: rule explicitly.** The spec says "grace-window relaunch for
   accidental exits" — if "accidental" includes reload, add the breadcrumb; if not,
   pure React state is simpler and sufficient.

3. **Slice-1 act catalog + the email deferral.** Confirm the slice-1 acts are
   note + reference + message + quote-escalation (all existing endpoints), and that
   **free-form email compose is DEFERRED** until the Email Primitive ships a
   compose→send endpoint. **Recommend: confirm the deferral** (the DM scenario's
   "email the price" is satisfiable in slice 1 via the transactional
   `/price-management/send-price-list` send, if desired).

*Minor build-time notes (not blocking Type B — flagged for the build):* adding
`"park"` to the `WidgetRendererProps.surface` union (one line, clarity); mounting
`ParkProvider`/`ParkHost` as a root-level sibling (like `PeekHost`) that both the
command-bar summon and the host can consume but that **must not** feed
`CommandBarProvider.focusIsOpen`.
