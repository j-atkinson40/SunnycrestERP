# The sweep: every route `e8e86328` introduced

**Read-only. Nothing fixed. 2026-10-03.**

Three questions, asked of each route `e8e86328` introduced on 2026-03-17:

1. Does the handler's call match the callee's signature?
2. Does a `response_model` exist?
3. Does the request schema accept what the frontend actually sends?

## The headline

**14 of 34 routes raise 500 on every call.** Not "can fail" — raise
unconditionally, on any input, for any tenant, and have done since the day they
shipped. The product-library 500 found during 2b-3 Commit 2 was not an isolated
defect. It was one of fourteen.

**All 14 are `e8e86328` originals. All 6 routes added to these files since then
bind correctly.** That split is the finding: this is not a codebase-wide habit,
it is one commit that was never executed.

| | count |
|---|---|
| routes `e8e86328` introduced | **28** |
| present at HEAD | 34 (6 added later; 0 removed) |
| raise 500 unconditionally | **14** — all 28-originals |
| carry a `response_model` | **0 of 34** |
| frontend payloads the schema rejects or truncates | **4 of 8** |
| frontend calls pointed at a path that does not exist | **5** |

⚠️ **The commit body claims "26 tenant endpoints + 5 admin endpoints".** Measured
from the commit's own files: **23 tenant + 5 admin = 28**. Not inherited — counted.

## Q1 — handler calls vs callee signatures: 14 failures, two mechanisms

### (a) Ten routes call a function that does not exist — `AttributeError`

The route layer and the service layer were written with different vocabularies.
Every one has an obvious twin that was never wired to it:

| route | handler calls | service actually defines |
|---|---|---|
| `POST /imports` | `create_import` | `create_data_import` |
| `GET /imports` | `list_imports` | `list_data_imports` |
| `GET /imports/{id}` | `get_import` | `get_data_import` |
| `PATCH /imports/{id}` | `update_import` | `update_data_import` |
| `POST /imports/{id}/preview` | `preview_import` | `preview_data_import` |
| `POST /imports/{id}/execute` | `execute_import` | `execute_data_import` |
| `POST /imports/white-glove` | `request_white_glove` | `request_white_glove_import` |
| `POST /check-in-call` | `schedule_check_in` | `schedule_check_in_call` |
| `GET /admin/analytics` | `get_analytics` | `get_onboarding_analytics` |
| `GET /admin/imports` | `list_white_glove_imports` | `list_all_white_glove_imports` |

⚠️ **Nothing catches this at import time.** `module.missing_attr` resolves at
CALL time, so the app boots, the routes register, OpenAPI renders them, and 200
days of deploys go green. The entire data-import wizard — the five-step flow the
commit message advertises — has never completed a single step.

### (b) Four routes pass more positional arguments than the callee accepts — `TypeError`

Same shape as the product-library 500. **Two are worse than arity:**

| route | call | signature | beyond arity |
|---|---|---|---|
| `POST /scenarios/{k}/advance` | `(db, company.id, scenario_key, data.step_key, data.result)` | `(db, tenant_id, scenario_key, step_number: int)` | `step_key` is a **str** into `step_number: int`; `result` has nowhere to go |
| `POST /product-library/import` | `(db, company.id, data.template_ids, current_user.id)` | `(db, tenant_id, items: list)` | — (the queued repair) |
| `POST /integrations` | `(db, company.id, data.model_dump(), current_user.id)` | `(db, tenant_id, integration_type: str)` | passes a **dict** where a `str` is declared |
| `PATCH /integrations/{id}` | `(db, company.id, integration_id, data.model_dump())` | `(db, integration_id, tenant_id, **kwargs)` | ⚠️ **`tenant_id` and `integration_id` are TRANSPOSED** — correct arity would still cross-wire them |

The transposition is the one to note. Fixing the arity on that route without
reading the signature would produce a call that binds, returns 200, and looks up
an integration by company id inside a tenant scoped by integration id.

## Q2 — `response_model`: 0 of 34

Not one route in either file declares one. Consequences, in order of how quietly
they bite:

- **No response contract.** Handlers return ORM objects and raw dicts; whatever
  the model happens to hold is what ships, including columns added later.
- **OpenAPI documents nothing.** Every response is an untyped `{}`, so the
  frontend's `onboarding.ts` types are hand-maintained guesses — which is exactly
  how `preset` / `category` / `default_unit` / `is_manufactured` survived in
  `ProductTemplate` after the catalog stopped having them (removed in 2b-3).
- **No field filtering.** `GET /checklists` (admin, cross-tenant) and
  `GET /integrations` return model objects directly.

⚠️ Treat this as one finding, not 34. It is a convention that was never adopted
in these two files, and a sweep that lands `response_model` on 34 routes is a
behaviour change on all 20 that currently work.

## Q3 — request schemas vs what the frontend sends: 4 of 8 wrong

Validated by feeding each schema the exact payload, not by reading field lists.

| route | frontend sends | schema requires | result |
|---|---|---|---|
| `POST /product-library/import` | `template_ids`, **`products`** | `template_ids` | **silently drops `products`** |
| `POST /imports` | `import_type`, `source_format` | `import_type`, **`file_name`** | **422** |
| `POST /integrations` | `integration_type` | **`provider`** | **422** |
| `POST /check-in-call` | `scheduled` | **`decision`** | **422** |
| `POST /help/dismiss` | `help_key` | `help_key` | ✓ |
| `PATCH /checklist/items/{k}` | `status` | `status?`, `skipped?` | ✓ |
| `POST /imports/white-glove` | `import_type`, `description`, `contact_email` | same | ✓ |
| `POST /scenarios/{k}/advance` | `step_key`, `result` | same | ✓ |

The three 422s never reach the Q1 defect underneath them — `POST /imports` and
`POST /integrations` would hit an `AttributeError` and a `TypeError` respectively
if the body ever validated. **Each of those routes has two independent defects
stacked**, and fixing the schema alone converts a 422 into a 500.

`POST /product-library/import` is the ruled case: the frontend's `products`
array carries `template_id` / `price` / `sku`, the licensee's prices are
tenant-authored data, and the schema must accept them.

## Not asked for, found anyway

**Five frontend functions call `/onboarding/...` instead of
`/tenant-onboarding/...`** — a different router, and the paths do not exist on
it. These 404 rather than 500:

```
getDataImport    -> GET   /onboarding/imports/{id}
updateDataImport -> PATCH /onboarding/imports/{id}
previewImport    -> POST  /onboarding/imports/{id}/preview
executeImport    -> POST  /onboarding/imports/{id}/execute
updateIntegration-> PATCH /onboarding/integrations/{id}
```

Confirmed absent from `onboarding.py` (control: that router's real paths are
`/templates`, `/templates/{id}`, …). So four of the ten `AttributeError` routes
are additionally **unreachable from the only client that would call them** — the
500 and the 404 have been hiding each other.

**`GET /debug-init` was added to `tenant_onboarding.py` after `e8e86328`** and is
mounted in the tenant API. Outside this sweep's scope; flagging it because a
route named `debug-init` on a production router deserves a decision.

## What this changes about 2b-3

2b-3 closed structurally at Commit 4 and its acceptance bar — *a licensee can
complete the onboarding product step* — is **not met**. This sweep says the gap
is wider than the import route:

- `GET /product-library` — **works** (Commit 2; 200, 52 products, 6 sections)
- `POST /product-library/import` — **500**, plus a schema that drops the prices
- `POST /checklist/items/{k}/complete` — **binds OK**
- `quick_orders` unlock — downstream of the checklist item

So the product step needs the import repair and nothing else in this list. The
other thirteen 500s are the *data-import wizard*, the *integration setup flow*,
the *scenario player*, the *check-in call*, and the *admin analytics dashboard* —
five more features from the same commit, each advertised in its message, none of
which has ever run.

## Method notes, including two of my own errors

- **I audited the wrong module first.** The routes call
  `tenant_onboarding_service`; I parsed `onboarding_service`, because that is the
  file 2b-3 edited. The first run reported **zero arity findings across 34
  routes** and read as clean. It had matched 12 of 34 edges and silently
  inspected nothing on the other 22. A constructed name — the module I expected
  rather than the one imported.
- **The clean result was caught by asking for the edge count, not by reading the
  output.** "Zero findings" and "nothing inspected" are the same sentence. Every
  stage below reports a non-zero control first.
- **`getattr` on the imported module, not AST**, for "does this callee exist" — a
  façade can re-export dynamically and AST cannot see it. `tenant_onboarding_service`
  is in fact a 263-line façade over `onboarding_service`, and resolving through it
  is why the ten absences are real rather than parse artifacts.
- **`inspect.signature().bind()`, not arity arithmetic**, for the call check —
  with a positive control asserting it rejects the exact shape that shipped the
  200-day 500 (`(db, company.id, form=...)`).
- **Pydantic, not field lists**, for Q3 — with controls both ways (a known-good
  payload accepted, a known-bad rejected).
- **zsh glob-expanded `--include=*.ts` again**, returning a confident zero
  frontend callers. Second instance this arc. Caught by a control requiring
  `apiClient` to return a large number; quoted globs return 33 call sites.

## Fix nothing — but note the ordering hazard

Per the dispatch, nothing here is repaired. One sequencing note for whoever does:

⚠️ **Three of these routes have two stacked defects, and repairing the outer one
converts a 422 into a 500.** `POST /imports` and `POST /integrations` fail
validation before reaching a call that would fail anyway. A schema fix that ships
alone makes the failure louder and later — a 422 naming the missing field is a
better diagnostic than an `AttributeError` traceback. Repair the pair together,
or repair the inner defect first.
